5. Backend architecture

No backend exists yet. This section is the recommended design. It is a modular monolith: one deployable API service plus a worker process, sharing one PostgreSQL database. This is the simplest architecture that meets V1’s needs, and modules can be split out later if load requires it.

5.4 Authentication and authorization

Authentication

  • Email and password registration. Passwords hashed with Argon2id. Email verified with a 6-digit code (valid 10 minutes, at most 5 attempts, resend limited). The app’s /verify screen already expects a 6-digit code.
  • Short-lived access token (JWT, about 15 minutes) and a rotating refresh token stored server-side per device. “Remember me” off = session ends when the app restarts. The devices list in Account & security reads the sessions table; signing out a device revokes its refresh token.
  • Password reset, change email and change phone all use one-time codes. Two-step verification (prefs.twoFactor) asks for an SMS code (or TOTP) at each new sign-in.
  • Rate limits on sign-in, code requests and code checks per account, IP and device.
  • DECISION Additional sign-in methods (Google, Apple) and the age policy (blueprint F01–F04). If any third-party sign-in is offered on iOS, Sign in with Apple must be offered too (App Store rule).

Authorization

  • The server stores approved_roles and the active_role per account. Switching (PUT /v1/me/workspace) is refused for a role that is not approved.
  • Each endpoint declares the roles it accepts (guards) and checks ownership in the query (for example WHERE provider_id = :me). Never trust ids or roles sent by the client.
  • Staff permissions (admin, reviewer, support, finance, moderator) live in a separate table, require two-step verification, and every staff decision writes an audit log entry (actor, action, target, note, time).

5.6 Realtime, notifications and messaging

  • One authenticated WebSocket connection per signed-in app instance. Server events: message.created, conversation.read, notification.created, booking.updated, request.created, ticket.checked_in. Use Redis pub/sub so several API instances can deliver events.
  • When the user is offline, the same events go out as push notifications (Expo push service → FCM / APNs). Tapping a push opens its deep link (for example /booking/b3).
  • The home attention banner and dashboard use an action queue endpoint that returns open items: payment failed, quote received, accepted and awaiting payment, change requested, event cancellation pending, invitations, unpaid contributions, friend requests, support replies, application updates and (for providers) new requests.

5.7 Media

  • The app asks for an upload URL (POST /v1/media/uploads), uploads directly to object storage, then sends the media id with the post, comment, avatar or listing.
  • A worker checks the file type, strips location metadata (EXIF), creates sizes (thumbnail, feed, full) and publishes CDN URLs.
  • Limits per kind are configuration, not code (file size, count per post or comment). Deleting a post or account deletes its media.
  • DECISION Video posts and live streaming need a video service (for example Mux or Cloudflare Stream). V1 can launch with photos only and keep the video and live screens behind a feature flag.

5.8 Search and location

  • Venues and events store a geographic point (PostGIS geography(Point)) set by geocoding the address. Distance filters use ST_DWithin; results return distanceKm from the user’s location.
  • Text search across events, artists, lessons, venues, communities, organizers and people uses PostgreSQL full-text search plus trigram similarity. A dedicated search engine is only needed later.
  • DECISION Exact venue address visibility before booking (blueprint F06–F07). Until decided, return the area and approximate pin publicly and the exact address only to confirmed participants.
