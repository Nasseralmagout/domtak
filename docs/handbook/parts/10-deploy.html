10.3 Backend deployment

  1. CI builds one Docker image per commit; the same image runs the API and (with another command) the worker.
  2. Merges to main deploy to staging automatically. Production deploys from a release tag after manual approval.
  3. Database migrations run as a separate step before the new version starts. Use expand-then-contract changes so the old and new versions both work during a deploy.
  4. Health endpoints: /health/live (process up) and /health/ready (database and Redis reachable). Roll back automatically if the new version is not ready.
  5. Run at least two API instances behind a load balancer with TLS; scale on CPU and latency. WebSocket connections need sticky sessions or the Redis adapter.
  6. Backups: daily automated database snapshots plus point-in-time recovery; test a restore before launch and every quarter. Object storage versioning on media.
  7. Monitoring: error rates and latency per endpoint, job queue depth and failures, webhook failures, payment reconciliation mismatches, push and email delivery failures. Alerts go to an on-call channel.

10.4 Web app

  • Already configured: vercel.json at the repository root and in mobile/ installs with npm ci, builds with npm run build:web (Expo static export to mobile/dist) and rewrites every path to index.html (single-page app).
  • Vercel project settings: Root Directory empty (repository root) or mobile; Framework Preset “Other”. Set the EXPO_PUBLIC_* variables for Preview and Production.
  • Add security headers in vercel.json (Content-Security-Policy allowing the API, Stripe and Maps domains; Strict-Transport-Security; X-Content-Type-Options; Referrer-Policy) and a cookie consent banner before any non-essential tracking.
  • The admin console is part of the web app and is only reachable for staff accounts (server-enforced).

10.5 Android release

# one-time: npx eas-cli@latest init ; npx eas-cli@latest credentials -p android
npx eas-cli@latest build -p android --profile preview      # internal APK for testers
npx eas-cli@latest build -p android --profile production   # AAB, versionCode auto-incremented
npx eas-cli@latest submit -p android --latest              # upload to the Play Console
  • Release through Play Console tracks: internal testing → closed testing → production (staged rollout).
  • Complete the store listing, data safety form (location, photos, payments, messages, identifiers), content rating, target audience, and the account deletion URL (the app already has in-app deletion).
  • Keep Play App Signing enabled; EAS manages the upload keystore. Back up credentials in the company account.

10.6 iOS release

npx eas-cli@latest build -p ios --profile production        # EAS creates certificates and profiles
npx eas-cli@latest submit -p ios --latest                    # upload to App Store Connect / TestFlight
  • Test through TestFlight (internal, then external testers) before App Review.
  • App Review needs: a working reviewer account with sample data, privacy “nutrition label” answers, purpose strings for camera (present) and location (to add), in-app account deletion (present), the Pro plan as an in-app purchase, and Sign in with Apple if any other third-party sign-in is offered.
  • supportsTablet is false: the app ships for iPhone only.

10.7 Build profiles and over-the-air updates

Recommended eas.json (extends the current file):

{
  "cli": { "version": ">= 16.0.0", "appVersionSource": "remote" },
  "build": {
    "development": { "developmentClient": true, "distribution": "internal", "channel": "development" },
    "preview":     { "distribution": "internal", "channel": "preview", "android": { "buildType": "apk" } },
    "production":  { "autoIncrement": true, "channel": "production", "android": { "buildType": "app-bundle" } }
  },
  "submit": { "production": {} }
}
  • Add expo-updates and set a runtime version policy so an update only reaches builds with the same native code.
  • JavaScript-only fixes: npx eas-cli@latest update --channel production. Changes to native modules or app.json need a new store build.
  • Check the Expo SDK 57 documentation for the exact expo-updates and eas.json options before applying.
